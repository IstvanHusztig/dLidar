golden_replay.sh shell

Replays the same packet log through a base revision and the working tree, then compares every recording file and the console log byte for byte. Use it for changes that must not change the output, such as the clean-architecture refactor. Use compare_recording_formats.sh instead when the format itself changes.

tools/golden_replay.sh [BASE_REV] [PACKETS_BIN] [SECONDS] [OUT_DIR]
ArgumentDefaultMeaning
BASE_REV36eceadThe reference revision (golden base of the clean-architecture change)
PACKETS_BIN~/PointCloudDump/packets0001.binThe packet timing log to replay
SECONDS60Replay only the first N seconds; 1e9 replays the whole log
OUT_DIRa new temp directoryGets base/ and new/, each with rec/ and console.log
GOLDEN_COMPARE_ONLY=1 (env)unsetSkip building and replaying; only compare an existing OUT_DIR
  • The base is built once in a temporary git worktree (sharing the 3rd/ LASzip checkout) and cached in ~/.cache/dlidar_golden/<hash>. Both sides need the replay_capture CMake target.
  • Exit code 0 means every file is identical; each file is listed as same, DIFFERS, MISSING or EXTRA.
  • Run it on the Pi (aarch64). Every target is built with -ffp-contract=off, so the -O2 replay does the same arithmetic as the -O0 bin/dLidar.

check_architecture.py Python

Checks the #includes of src/ against the layer rule: domain/ includes only standard headers and domain/; application/ adds application/; an adapter includes the core and itself, never app/ or another adapter; app/ includes anything. ctest runs it as architecture, and its self-test as architecture_selftest.

python3 -I tools/check_architecture.py [--strict] [SRC_DIR]
python3 -I tools/check_architecture.py --self-test

--strict also rejects sources outside the layer directories and a leftover include/ directory.

compare_recording_formats.sh shell

Replays the same packets through an older dLidar commit and the working tree. It then checks that the standard recording content is identical and the newer additions are consistent. Run it after any change to what a recording contains. The rule is that changes only add data and dMapper must read new recordings exactly as old ones.

cmake --build build                      # LASzip is linked from build/3rd/lib
tools/compare_recording_formats.sh [OLD_REV] [PACKETS_BIN] [SECONDS] [OUT_DIR]
ArgumentDefaultMeaning
OLD_REVd68191bA header-only commit of recording format 1 whose include/ writes the reference recording (d68191b is the last recording format 1 commit)
PACKETS_BIN~/PointCloudDump/packets0001.binThe packet timing log to replay
SECONDSwhole logReplay only the first N seconds. The 800-chunk capture limit still applies.
OUT_DIRa new temp directoryGets old/, new/, old.log and new.log. old/ and new/ must be empty.
PYTHON (env)python3An interpreter with laspy[lazrs] and numpy

The script:

  1. Extracts include/ of OLD_REV with git archive into a temp directory.
  2. Builds the frozen tools/replay_capture_format1.cpp against those old headers, and the working tree's bin/replay_capture with CMake.
  3. Replays the packet log through both into OUT_DIR/old and OUT_DIR/new.
  4. Runs tools/verify_recording_format.py on the two folders and exits with its status.
python3 -m venv ~/venv-laspy && ~/venv-laspy/bin/pip install "laspy[lazrs]" numpy
PYTHON=~/venv-laspy/bin/python tools/compare_recording_formats.sh d68191b ~/PointCloudDump/packets0001.bin 30

replay_capture C++

Replays the packet sequence of a recording's packetsNNNN.bin into a new recording, without the sensor. The input is the L2 stamps, seq, host arrival times, time_increment and point_num. The output goes through the real capture code, the same path as a live recording.

bin/replay_capture ~/PointCloudDump/packets0001.bin OUT_DIR [SECONDS] [TARGET_CHUNKS]
  • OUT_DIR must exist. The recording takes the next free session number in it, as a real capture does.
  • The packet log holds only timing, so packet contents are synthetic. The rays of the L2 sensor model, with the same formula as the parser, hit a box room around a stationary sensor. Ranges carry ±3 mm of noise and 2 % have no return. Intensity depends on wall reflectivity, incidence and range. The IMU is at rest (1 g on +Z). Calibration and state values are fixed plausible numbers.
  • Everything is deterministic. Host times come from the log, so two builds fed the same log write byte-identical files wherever their formats agree.
  • The output is not a measurement: odometry on it gives a stationary trajectory. Use it for format and pipeline checks, not for tuning.
  • Its packets go through the production path: SyntheticL2Source → UnitreeL2Sensor → ScannerController/RecordSession → FileRecordingStorage. An optional fourth argument sets the chunk limit (default 800).

verify_recording_format.py Python

Compares a format 1 and a format 2 recording made from the same packets. Each folder must hold one recording with session number 0001, as the compare script produces.

python3 tools/verify_recording_format.py OLD_DIR NEW_DIR

It needs laspy with a LAZ backend (pip install "laspy[lazrs]" numpy). It prints one PASS/FAIL line per check, ends with ALL PASSED, and exits non-zero if any check fails.

GroupChecks
Same standard contentLAS 1.2 / format 1; same scale, offset, bounds and point count; the legacy count is filled. X/Y/Z, gps_time, intensity, user_data, classification, returns, point source, scan angle and flags are identical point for point. user_data is 1. imu0001.csv and packets0001.bin are byte-identical. Every old timing0001.json key keeps its value. No new .csv/.las/.laz file.
Extra bytesNames and types are range, raw_range, sample_index, packet_seq, alpha, theta. |xyz| − range is within the a/b axis offsets. sample_index is in 0..299. range equals range_scale·(raw_range+range_bias) in float32.
SidecarOne packetstate0001.tsv row per point packet in packets0001.bin, with the same seq and stamp. stamp_ns = l2_stamp_ns − zero_l2_ns. Each point's packet_seq and gps_time match its packet row exactly. The seq gaps match the packet log.

replay_packets C++

Replays a recording's packet timing log through the IMU timestamping: ImuTimeline in auto, sensor and host_aligned mode, and the old host-stamped method.

bin/replay_packets ~/PointCloudDump/packets0001.bin [imu_offset_ns]

It prints the auto-mode timing report (as in timingNNNN.json). For every 60 s it also prints how far the host_aligned fallback and the old method are from the L2 IMU stamps. See docs/imu_lidar_time_alignment.md.

check_imu_timestamps.py Python

Reports the row count, time span, rate, non-increasing timestamp/timestampUnix steps, and the median, minimum and maximum spacing of an IMU CSV.

python3 tools/check_imu_timestamps.py ~/PointCloudDump/imu0001.csv

repair_imu_timestamps.py Python

Rewrites the timestamps of an imu*.csv recorded before the IMU timestamp fix. The measurement columns are copied unchanged, and the original file is never modified.

python3 tools/repair_imu_timestamps.py OLD.csv [-o OUT.csv] [--mode anchored|uniform] [--force]
  • anchored (default): keeps each batch's first real sensor stamp and spreads the batch's samples evenly up to the next one. It falls back to uniform if the anchors don't increase.
  • uniform: keeps the first and last value and spaces all rows evenly between them.
  • It only evens out the spacing. The IMU stays on the host clock, so the 50–80 ms lag of those old recordings remains.
The default output is <input>_fixed.csv, next to the input. dMapper reads every .csv in a recording folder, so write the output elsewhere with -o, or move the original out, before running dMapper on that folder.
