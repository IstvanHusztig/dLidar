What it does

dLidar is the application of a handheld scanning device. It reads a Unitree L2 LiDAR, which also contains an IMU, and writes everything into files. Our SLAM solution dMapper then turns those files into a trajectory and a map. dLidar itself does no mapping: it records the raw data as accurately as possible, with points and IMU samples on one common clock.

Unitree L2~64,000 points/s in packets of 300, plus IMU samples (acceleration, rotation rate), sent over Ethernet (UDP).
→
Raspberry Pi running dLidarA Pi Zero 2 W on the device; development and tests on a Pi 5. Converts, timestamps and writes.
→
~/PointCloudDump/One numbered set of files per recording: lidarNNNN.laz, imuNNNN.csv and diagnostics.
→
dMapperReads every .laz and .csv in the folder and runs SLAM.

The L2 is mounted vertically: its own +Z axis points forward and its cable outlet points up. dLidar rotates every point and IMU sample into the device frame: +X forward, +Y left, +Z up.

Today a recording is started by launching ./bin/dLidar. It ends after 200 chunks (about a minute) or on Ctrl-C. Push buttons, status LEDs and a Bluetooth link to a phone are planned, and the architecture is prepared for them.

A recording, step by step

The colour on the left of each step shows which layer does the work (see Architecture).

app (wiring) adapters (L2, files, console) application (use cases) domain (rules)
1. Startmain.cpp
Installs the signal handlers. Finishes any recording a crash or power loss left behind (into recovered_<time>/). Connects to the L2 at 192.168.0.62, builds the parts and asks the ScannerController to start a recording.
↓
2. Sensor start-upPreparing · LiveL2Source
Restarts the L2's rotation, then prints its lens dirtiness, time delay and firmware/hardware versions. Then reads away the packets that piled up meanwhile for 2 s, so stale packets don't enter the recording. If the L2 does not answer within 10 s, the recording ends in Error and no files are written.
↓
3. Capture loopRecording · RecordSession
The storage opens now, which creates the next free file number NNNN. Then one packet is read at a time: sensor.Poll() returns an IMU packet or a point packet, plus the host time it arrived.
↓
4. DecodeUnitreeL2Sensor · l2_conversion
Turns the L2's packet into points in the sensor frame: x, y, z in metres, intensity, measured range, scan angles, and each point's time. Also turns IMU packets into acceleration (m/s²) and rotation rate (rad/s) with the L2's own timestamp.
↓
5. Timing, mount, filterCaptureTiming
  • The first point packet with points sets the time zero.
  • Points get times relative to it.
  • Points outside 0.1–100 m or with intensity below 5 are dropped.
  • The mount rotation is applied, and IMU acceleration becomes g.
  • ImuTimeline gives the IMU samples their times on the same clock.
↓
6. ChunksChunkAssembler · LensMonitor
Collects points (and the IMU samples released with them) into chunks of at least 14,000 points. Each full chunk goes into a queue. Every 10 s the lens dirtiness is checked; above 5% a warning is shown.
↓ queue (a separate writer thread, so a slow SD card never delays reading packets)
7. WritingFileRecordingStorage
IMU rows are appended to imuNNNN.csv. Points go in raw form to points_tempNNNN.bin, and the packet log and packet state rows are written alongside. Everything on disk is always in a state that can be recovered.
↓ after 200 chunks or Ctrl-C
8. FinishingFinalizing · laz_encoder
The L2 stops rotating. The last chunk, the IMU timing summary and timingNNNN.json are written. The temporary point file is compressed into lidarNNNN.laz (written as .laz.tmp, renamed when complete) and is deleted last. The state returns to Idle.

Time, axes and units

SLAM needs points and IMU samples on one clock, to well under a millisecond. This is the most delicate part of dLidar.

  • The clock is the L2's own. Both point packets and IMU packets carry the L2's timestamp. Host arrival times are not used for the data: the L2 sends IMU samples in bursts, and stamping them on arrival (as the SDK does by default) made the IMU lag the points by 50–80 ms.
  • Time zero is the stamp of the first point packet that has points. LAZ gps_time is in seconds since the zero, and the IMU CSV timestamp in nanoseconds since the same zero.
  • Checking the IMU clock. ImuTimeline watches the first 2 s. It checks that the IMU stamps increase, are evenly spaced, run at the host's rate and share the points' clock. If not, it switches to a fallback (host_aligned) that rebuilds even IMU times from the arrival times and maps them onto the L2 clock. The choice and its evidence go into timingNNNN.json. Details: imu_lidar_time_alignment.md.
  • Axes: the device frame is +X forward, +Y left, +Z up. The mount (kMount) only selects and negates axes, never multiplies, so values keep their exact bits.
  • Units: metres, seconds, radians, rad/s; IMU acceleration in g. Intensity is the L2's raw 0–255 value.

The files of a recording

Each recording takes the next free number NNNN, so earlier recordings are never overwritten. dMapper reads every .csv, .las and .laz in the folder, so no other file may use those extensions. Field by field: l2-recording-format.md.

FileContentUsed by
lidarNNNN.lazThe point cloud (LAS 1.2, point format 1): x, y, z, intensity, time, plus extra bytes (range, raw range, sample index, packet seq, scan angles).dMapper
imuNNNN.csvOne row per IMU sample: gyro x/y/z (rad/s), accel x/y/z (g), id, timestamp (ns since zero), Unix timestamp.dMapper
timingNNNN.jsonHow the IMU times were made, clock rates, latencies, drops, sensor and software versions.diagnostics
packetsNNNN.binArrival time and L2 stamp of every packet; can be replayed offline (bin/replay_packets, bin/replay_capture).diagnostics, tests
packetstateNNNN.tsvOne row per point packet: L2 temperatures, voltages, dirtiness, calibration.diagnostics
points_tempNNNN.binRaw points while recording; the source for crash recovery. Gone after a normal end.dLidar only

Files are created only once the sensor has started. A failed start or a stop during the start-up writes nothing.

Stops, crashes and failures

EventWhat happens
Ctrl-C (or SIGTERM / SIGHUP) onceNormal stop: the recording is finished and all files are complete.
Ctrl-C twiceThe process is killed at once. The next start finishes the leftover recording into recovered_<time>/, or run ./bin/dLidar --finalize to finish it in place.
Crash or power lossLike a kill. A crash also cuts the CSV back to its last complete row. On the next start the points are recovered and a partial last CSV row is trimmed.
L2 does not answerError after 10 s of waiting; no files.
Storage cannot open or failsThe capture stops at once (rather than filling the memory), what was written is closed, Error.
Any internal exceptionThe chunks already captured are written, the files closed, the L2 stopped, Error. The process keeps running and accepts a new start.
SD card slower than the sensorChunks wait in memory; past 50 waiting chunks a warning is shown. Chunks are never dropped.

Architecture

The code follows Clean Architecture (Robert C. Martin): the rules of recording sit in the middle and know nothing about the L2, files or the console; those sit outside and plug in through interfaces (ports). That way the LiDAR can be replaced and buttons, LEDs or a phone link can be added without touching the recording logic.

app · composition root · src/app/
main.cpp (command line, wiring), device_config.h (IPs, mount, chunk limit), signals.h
adapters · the outside world · src/adapters/
unitree_l2/ (the sensor, Unitree SDK), storage/ (files, LAZ via LASzip, recovery), console/ (texts)
application · use cases and ports · src/application/
ports/ (LidarSensor, RecordingStorage, DeviceEvents), capture/ (RecordSession, CaptureTiming, ChunkAssembler, LensMonitor), device/ (ScannerController, EventHub)
domain · data and pure rules · src/domain/
recording/ (PointRecord, ImuSample, file records), timing/ (ImuTimeline, ImuTimestamper), geometry/ (AxisMap, PointFilter)

The dependency rule

Code may only include code of its own layer or of layers further in. The domain sees only the C++ standard library; the application sees the domain; an adapter sees the core and its own folder, never another adapter; only app/ sees everything. The build enforces this: the core library (dlidar_core) has neither the Unitree SDK nor LASzip on its path. The test tools/check_architecture.py (ctest architecture) checks every #include.

Threads and states

Idle→Preparing→Recording→Finalizing→Idle  or Error

The ScannerController holds the state. It accepts a start only in Idle or Error and runs one recording at a time. Each input channel (today the Ctrl-C signal; later buttons and the phone) calls StartRecording / StopRecording from its own thread.

ThreadDoes
mainWiring, then waits for the recording to end.
controller workerRuns the recordings: sensor start-up, packet loop, timing, chunking, and sends the events.
writer (one per recording)Hands the chunks to the storage, so a slow SD card never delays packet reading.
one per async output channelDelivers events to that channel (LEDs, phone) through a small queue; a slow or broken channel never affects a recording.

Adding features

  • Another LiDAR: a new adapter folder implementing LidarSensor, selected in main.cpp, with its mount in device_config.h. No change to the core.
  • A push button (input): an adapter that calls StartRecording / StopRecording. It will replace today's fixed 200-chunk limit.
  • LEDs or a phone link (output): an adapter implementing DeviceEvents, registered with hub.AddAsync(...).
Refactors must not change any recording. tools/golden_replay.sh replays a real packet log through an older build and the current one and compares every file byte by byte. See tools.html.
