What it does

dLidar is the application of a handheld scanning device. It reads a Unitree L2 LiDAR, which also contains an IMU, and writes everything into files. Our SLAM solution dMapper then turns those files into a trajectory and a map. dLidar itself does no mapping: it records the raw data as accurately as possible, with points and IMU samples on one common clock.

Unitree L2~64,000 points/s in packets of 300, plus IMU samples (acceleration, rotation rate), sent over Ethernet (UDP).
→
Raspberry Pi running dLidarA Pi 5 with 1 or 2 GB RAM on the device; development and tests on a Pi 5 dev board. Converts, timestamps and writes.
→
~/PointCloudDump/One numbered set of files per recording: lidarNNNN.laz, imuNNNN.csv and diagnostics.
→
dMapperReads every .laz and .csv in the folder and runs SLAM.

The L2 is mounted vertically: its own +Z axis points forward and its cable outlet points up. dLidar rotates every point and IMU sample into the device frame: +X forward, +Y left, +Z up.

Today a recording is started by launching ./bin/dLidar. It ends after target_chunks chunks (default 1500, see Settings) or on Ctrl-C. Push buttons, status LEDs and a Bluetooth link to a phone are planned, and the architecture is prepared for them.

Settings

dLidar reads its settings from ~/.config/dlidar/dlidar.toml, or from the file given with ./bin/dLidar --config PATH. Without that file it uses the built-in defaults (src/app/device_config.h): the Unitree L2 as it has always been set up. A key that is left out keeps its default. At start-up dLidar prints which settings it used (settings: ... (sensor ...)).

The file is a small subset of TOML: [section] lines, key = value lines with a "string", an integer, a decimal number or true/false, and # comments. Anything else (arrays, inline tables, multi-line strings, dotted keys), an unknown section or key, and a wrong or out-of-range value stop dLidar with the file name and line number before it touches the sensor or any file, so a typo never falls back to a default silently. The file never goes into ~/PointCloudDump/.

The colour on the left of each step shows which layer does the work (see Architecture).

Installs the signal handlers. Finishes any recording a crash or power loss left behind (into recovered_<time>/). Connects to the L2 at 192.168.0.62, builds the parts and asks the ScannerController to start a recording.
↓
2. Sensor start-upPreparing · LiveL2Source
Restarts the L2's rotation, then prints its lens dirtiness, time delay and firmware/hardware versions. Then reads away the packets that piled up meanwhile for 2 s, so stale packets don't enter the recording. If no packet arrives for 10 s, or the status does not come within 60 s (after a restart the L2 sends points only after ~20 s of spin-up), the recording ends in Error and no files are written.
↓

The storage opens now, which creates the next free file number NNNN. Then one packet is read at a time: sensor.Poll() returns an IMU packet or a point packet, plus the host time it arrived.

Turns the L2's packet into points in the sensor frame: x, y, z in metres, intensity, measured range, scan angles, and each point's time. Also turns IMU packets into acceleration (m/s²) and rotation rate (rad/s) with the L2's own timestamp.
↓
5. Timing, mount, filterCaptureTiming
  • The first point packet with points sets the time zero.
  • Points get times relative to it.
  • Points outside 0.1–100 m or with intensity below 5 are dropped.
  • The mount rotation is applied, and IMU acceleration becomes g.
  • ImuTimeline gives the IMU samples their times on the same clock.
↓
6. ChunksChunkAssembler · LensMonitor
Collects points (and the IMU samples released with them) into chunks of at least 14,000 points. Each full chunk goes into a queue. Every 10 s the lens dirtiness is checked; above 5% a warning is shown. If no points arrive for 10 s, a watchdog stops the recording.
↓ queue (a separate writer thread, so a slow SD card never delays reading packets)
7. WritingFileRecordingStorage
IMU rows are appended to imuNNNN.csv. Points go in raw form to points_tempNNNN.bin, and the packet log and packet state rows are written alongside. Everything on disk is always in a state that can be recovered.
↓ after 200 chunks or Ctrl-C
8. FinishingFinalizing · laz_encoder
The L2 stops rotating. The last chunk, the IMU timing summary and timingNNNN.json are written. The temporary point file is compressed into lidarNNNN.laz (written as .laz.tmp, renamed when complete) and is deleted last. The state returns to Idle.

Time, axes and units

SLAM needs points and IMU samples on one clock, to well under a millisecond. This is the most delicate part of dLidar.

  • The clock is the L2's own. Both point packets and IMU packets carry the L2's timestamp. Host arrival times are not used for the data: the L2 sends IMU samples in bursts, and stamping them on arrival (as the SDK does by default) made the IMU lag the points by 50–80 ms.
  • Time zero is the stamp of the first point packet that has points. LAZ gps_time is in seconds since the zero, and the IMU CSV timestamp in nanoseconds since the same zero.
  • Checking the IMU clock. ImuTimeline watches the first 2 s. It checks that the IMU stamps increase, are evenly spaced, run at the host's rate and share the points' clock. If not, it switches to a fallback (host_aligned) that rebuilds even IMU times from the arrival times and maps them onto the L2 clock. The choice and its evidence go into timingNNNN.json. Details: imu_lidar_time_alignment.md.
  • Axes: the device frame is +X forward, +Y left, +Z up. The mount (kMount) only selects and negates axes, never multiplies, so values keep their exact bits.
  • Units: metres, seconds, radians, rad/s; IMU acceleration in g. Intensity is the L2's raw 0–255 value.

The files of a recording

Each recording takes the next free number NNNN, so earlier recordings are never overwritten. dMapper reads every .csv, .las and .laz in the folder, so no other file may use those extensions. Field by field: l2-recording-format.md. What recording format 2 added (per-point range, scan angles, packet state) and how it was verified: recording-format-2.html.

Architecture

The code follows Clean Architecture (Robert C. Martin): the rules of recording sit in the middle and know nothing about the L2, files or the console; those sit outside and plug in through interfaces (ports). That way the LiDAR can be replaced and buttons, LEDs or a phone link can be added without touching the recording logic.

app · composition root · src/app/
main.cpp (command line, wiring), device_config.h (IPs, mount, chunk limit), signals.h
adapters · the outside world · src/adapters/
unitree_l2/ (the sensor, Unitree SDK), storage/ (files, LAZ via LASzip, recovery), console/ (texts)
application · use cases and ports · src/application/
ports/ (LidarSensor, RecordingStorage, DeviceEvents), capture/ (RecordSession, CaptureTiming, ChunkAssembler, LensMonitor), device/ (ScannerController, EventHub)
domain · data and pure rules · src/domain/
recording/ (PointRecord, ImuSample, file records), timing/ (ImuTimeline, ImuTimestamper), geometry/ (AxisMap, PointFilter)

The dependency rule

Code may only include code of its own layer or of layers further in. The domain sees only the C++ standard library; the application sees the domain; an adapter sees the core and its own folder, never another adapter; only app/ sees everything. The build enforces this: the core library (dlidar_core) has neither the Unitree SDK nor LASzip on its path. The test tools/check_architecture.py (ctest architecture) checks every #include.

Threads and states

Idle→Preparing→Recording→Finalizing→Idle  or Error

The ScannerController holds the state. It accepts a start only in Idle or Error and runs one recording at a time. Each input channel (today the Ctrl-C signal; later buttons and the phone) calls StartRecording / StopRecording from its own thread.

ThreadDoes
mainWiring, then waits for the recording to end.
controller workerRuns the recordings: sensor start-up, packet loop, timing, chunking, and sends the events.
writer (one per recording)Hands the chunks to the storage, so a slow SD card never delays packet reading.
one per async output channelDelivers events to that channel (LEDs, phone) through a small queue; a slow or broken channel never affects a recording.

Adding features

  • Another LiDAR: a new adapter folder implementing LidarSensor, selected in main.cpp, with its mount in device_config.h. No change to the core.
  • A push button (input): an adapter that calls StartRecording / StopRecording. It will replace today's fixed 200-chunk limit.
  • LEDs or a phone link (output): an adapter implementing DeviceEvents, registered with hub.AddAsync(...).

New code and refactors follow the SOLID principles: one job per class, new features as new adapters instead of core edits, every port implementation interchangeable with the others, small ports with defaults for optional capabilities, and the core depending only on ports. See "SOLID" in docs/architecture.md.

Refactors must not change any recording. tools/golden_replay.sh replays a real packet log through an older build and the current one and compares every file byte by byte. See tools.html.

Signals

A signal is a small asynchronous notification that the Linux kernel delivers to a process. It carries no data, only a number such as SIGINT = 2 or SIGTERM = 15. It can arrive at any instruction. The kernel interrupts whatever the thread is doing, runs the function registered for that signal (the handler), and then resumes the interrupted code.

SourceExamplesSignals
Someone outside asks the process to stopCtrl-C in the terminal, kill <pid>, systemctl stop, SSH connection lost or terminal closedSIGINT, SIGTERM, SIGHUP
The process itself does something fatalnull pointer access, bad memory mapping, divide by zero, abort() or a failed assertSIGSEGV, SIGBUS, SIGFPE, SIGILL, SIGABRT

Every signal has a default action. For all the signals above, the default is to kill the process at once, so no destructors run, buffers aren't flushed and files aren't closed. A program can install its own handler with sigaction() to replace that default. The two exceptions are SIGKILL (kill -9) and power loss: nothing can catch those.

Why dLidar needs them. A recording does a lot of work at the end. points_tempNNNN.bin is read twice and encoded into lidarNNNN.laz.tmp, which is then renamed. The IMU CSV and timingNNNN.json get finished, and the temp file is deleted last. Without handlers, Ctrl-C would kill the process mid-recording and leave a raw temp file, no LAZ, and possibly a half-written CSV row that dMapper would choke on. Today signals are also the only way to stop a recording early (there's no push button yet). On the headless Pi, SIGTERM from systemd or SIGHUP from a dropped SSH session are the realistic ways a capture ends.

main.cpp calls InstallSignalHandlers() (src/app/signals.h) as its first statement, before anything can be recorded. It installs two groups of handlers and ignores one signal.

1. Stop signals (SIGINT, SIGTERM, SIGHUP) mean "please finish".

inline void OnStopSignal(int sig)
{
    if (StopRequested().exchange(true))   // was it already set?
    {   // second signal: give up
        signal(sig, SIG_DFL);
        raise(sig);
        return;
    }
    WriteStderr("\nStop requested, finishing the recording ...");
}
  • The first signal only sets an std::atomic<bool> flag. The handler does no cleanup itself. The rest of the program checks the flag at safe points. If the stop came during recovery or the L2 start-up, main.cpp exits without creating any files, because an empty file pair would end up in dMapper's input. During a recording, main.cpp hands &StopRequested() to the ScannerController. It becomes a StopToken (application/ports/stop_token.h) that RecordSession checks in its packet loop. When the flag is set, the loop ends and the normal shutdown path runs: drain the queue, flush the writer, finalize the LAZ. A Ctrl-C recording is therefore identical in format to one that hit 200 chunks.
  • A second signal means the user really wants out, for example because finalizing hangs. The handler restores the default action (SIG_DFL) and re-raises the signal, and the process dies. That's safe because of recovery: on the next start, the leftover points_tempNNNN.bin is finalized into recovered_<time>/.

2. Fatal signals (SIGSEGV, SIGBUS, SIGFPE, SIGILL, SIGABRT) mean "we're crashing, leave clean files".

inline void OnFatalSignal(int sig)
{
    int fd = CrashTruncateFd().load();
    if (fd >= 0)
        ftruncate(fd, CrashTruncateSize().load());  // cut CSV back to last full row
    signal(sig, SIG_DFL);
    raise(sig);                                      // die as the crash would have
}

After a crash the process can't keep running, because memory may be corrupted. It can still repair one thing first: the IMU CSV. ContinuousDataWriter keeps two atomics in adapters/storage/crash_guard.h up to date: the CSV's file descriptor and the byte size after the last complete row. The handler truncates the file to that size, so no partial line is left, and then re-raises the signal. The process still dies with the correct signal, so a core dump or the shell's exit status still reports a segfault. SA_RESETHAND makes the handler one-shot, so a crash inside the handler can't loop. The points are recovered on the next start, just as after a kill.

3. SIGPIPE is ignored. SIGPIPE is sent when the program writes to a closed pipe or socket, such as ./bin/dLidar | head or a closed log pipe. Its default action would kill the recording silently. With the signal ignored, write() returns an error (EPIPE) instead, and the program can handle it.

Why the handlers do so little. A handler can interrupt the program anywhere: inside malloc, while holding a mutex, or halfway through a printf. If the handler then calls a function that uses the same lock or heap, the program deadlocks or corrupts memory. POSIX therefore allows only async-signal-safe functions inside handlers. These are mostly raw system calls: write, ftruncate, signal, raise, _exit. That rule explains several details in the code:

  • It uses write(STDERR_FILENO, …), not std::cerr or printf. Those two use locks and buffers and aren't safe in a handler.
  • It only sets an atomic flag. Real work like finalizing the LAZ or joining threads happens in normal code that checks the flag, not in the handler.
  • The crash data is pre-computed into atomics. The fatal handler can't ask the writer object anything. It only reads two lock-free values that the writer kept current, then makes one system call.
  • The statics are initialized up front. InstallSignalHandlers() calls StopRequested(), CrashTruncateFd() and CrashTruncateSize() once beforehand. The first call to a function-local static runs a guarded initialization that may take a lock, and that must not happen for the first time inside a handler.

How it fits the architecture. Signals belong to the operating system, so they're handled in src/app, not in the core. The application layer never sees a signal: it only gets an abstract StopToken. Signals are just the first input channel of the ScannerController. Later, push buttons and the phone will call StartRecording / StopRecording on the same interface, and the recording code won't need to change.

Atomics

When two threads (or a thread and a signal handler) read and write the same plain variable, the result is undefined: the compiler may keep the value in a register, and the CPU may reorder or tear the access. std::atomic<T> makes each read and write indivisible and visible to the other side. dLidar uses atomics where a lock is impossible or overkill: the stop flag (written by the signal handler, read by the capture loop), the crash-guard file descriptor and size (written by the writer, read by the fatal handler), and the StopToken. exchange(true) in the stop handler sets the flag and returns the old value in one step, which is how the handler tells the first signal from the second.

Threads, mutexes and condition variables

The L2 sends ~64,000 points/s over UDP, and the socket's buffer is small. If the thread that reads packets stopped to write to a slow SD card, packets would be lost. dLidar therefore splits the work into threads (see Threads and states) and connects them with producer–consumer queues:

  • A mutex (std::mutex) protects the queue: only one thread at a time may push or pop. std::lock_guard / std::unique_lock take the lock and release it automatically at the end of the scope.
  • A condition variable (std::condition_variable) lets the consumer sleep until there is work: the writer waits with cv_.wait(lock, [&]{ return !queue_.empty() || !capturing_; }) and the capture thread wakes it after each push. The predicate guards against spurious wake-ups and tells the writer when to stop.
  • Two queue policies. The chunk queue in RecordSession is unbounded and never drops data; it only warns past 50 waiting chunks. The queues of async output channels in EventHub are bounded (64 events) and drop the oldest event when full, because a stuck LED or Bluetooth link must never block or slow a recording.

The ScannerController uses the same tools for its state: every command takes the mutex, reads the state and decides (a start is accepted only in Idle or Error), so commands from several input channels can't race each other.

Exceptions at thread boundaries

An exception that leaves the function of a std::thread calls std::terminate, which kills the whole process without cleanup. Every thread function in dLidar (controller worker, writer, async event channels) therefore ends in catch (const std::exception &) and catch (...). A failure turns into a warning and the Error state; the chunks already captured are written and the process stays ready for a new start. Exceptions from an output channel are caught and ignored, so a broken display can't end a recording.

RAII: cleanup in destructors

Resource Acquisition Is Initialization: an object acquires a resource (file, thread, lock) in its constructor and releases it in its destructor, which C++ runs automatically when the object goes out of scope, also during an exception. Examples: ~ContinuousDataWriter calls fsync and closes the CSV; ~ScannerController stops and joins its worker thread; the lock guards release their mutex. In main.cpp the controller lives in its own { … } block, so its thread is joined before sensor.Stop() runs. Member order matters too: worker_ is declared last in ScannerController, so the thread starts only after every member it uses exists.

Interfaces, ports and fakes

A port is a C++ class with only pure virtual functions (virtual bool Open() = 0;) and a virtual destructor. The core calls the port; at run time the call goes to whatever object was passed in. This is dependency inversion: RecordSession depends on LidarSensor, not on the Unitree SDK, so the SDK can't leak into the core. It also makes testing without hardware possible: the tests pass FakeSensor and MemoryStorage, and bin/replay_capture passes a SyntheticL2Source that replays a packet log through the real UnitreeL2Sensor.

Crash-safe files

Power can fail between any two instructions, so every file is written so that what is on disk is always either complete or recoverable:

  • Write to a temporary name, then rename. lidarNNNN.laz.tmp and timingNNNN.json.tmp are renamed when complete. A rename within one file system is atomic: the final name either doesn't exist or points to the complete file, never a half-written one.
  • Delete the source last. points_tempNNNN.bin is deleted only after the LAZ is renamed. If finalizing is interrupted, the next start sees the temp file and does it again.
  • Whole rows in one write(). The IMU rows of a chunk are formatted into one string and written with one system call. If the write fails, ftruncate cuts the file back to the last committed size; a crash does the same through the signal handler; recovery trims a partial last row after a power loss.
  • fsync on close forces the kernel to put the CSV on the SD card instead of keeping it in its cache.
  • A header in the temp file. The 16-byte header tells recovery the record size, so temp files of older builds (32-byte records) can still be finalized.

Two host clocks

Every packet's arrival is stamped with two Linux clocks (live_l2_source.cpp). CLOCK_MONOTONIC only ever runs forward at a steady rate and is never stepped, so it is used for all arrival timing, rates and latencies. CLOCK_REALTIME is wall-clock time; NTP or a user can step it (the Pi 5 keeps its real-time clock only with the optional battery, so without one its time can jump after boot once NTP syncs), so it is used only as the Unix anchor for timestampUnix. The data itself is timed on a third clock, the L2's own (see Time, axes and units).

UDP

The L2 talks over UDP: each packet is sent once, with no connection, no acknowledgement and no retransmission. Packets can be lost (a full socket buffer on the Pi, a bad cable) and nothing tells the sender. That's why the reading thread must never block on anything slow, why lost IMU samples are detected from the sequence numbers and timing, and why timingNNNN.json counts drops.

Constants and the k prefix

Names like kMount, kLidarIp, kTargetChunks and kRecordingFormatVersion are compile-time constants (constexpr / const). The k prefix is the Google C++ Style Guide rule for constants; it goes back to Hungarian notation and the early Mac Toolbox. Read a k… name as "fixed configuration value": the device settings in src/app/device_config.h are hardcoded, not read from a file. Many small headers are header-only and use inline functions and variables, so one definition is shared by every file that includes them; a function-local static (as in StopRequested()) is created on first use and exists once per program.

Reproducible floating point

Modern CPUs have a fused multiply-add (FMA) instruction that computes a*b + c with one rounding instead of two. Whether the compiler uses it depends on the optimisation level and how the code is split, so the same source could give results differing in the last bit between the -O0 bin/dLidar and the -O2 replay tools. Every target is built with -ffp-contract=off, which forbids that contraction. Results are then bit-identical across builds, and tools/golden_replay.sh can compare recordings byte by byte. The mount (AxisMap) follows the same idea: it only selects and negates axes, so values keep their exact bits.
