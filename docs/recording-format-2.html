dLidar recording format 2

What changed in dLidar's Unitree L2 recordings, so dMapper can later add an intensity normalization (range and incidence-angle correction). The full field reference is docs/l2-recording-format.md. For how dLidar works as a whole, see How dLidar works.

This change only adds data. Every format 1 field keeps its value, type and position. The IMU CSV is byte-identical. No new file in a recording folder ends in .csv, .las or .laz. Today's dMapper therefore reads a format 2 recording exactly as it read a format 1 recording.

Summary of changes

lidarNNNN.lazSix per-point attributes in LAS extra bytes. The record grows from 28 to 48 bytes; it stays LAS 1.2, point format 1. generating_software becomes dLidar recording format 2.

timingNNNN.jsonNew keys: recording_format_version, lidar_firmware_version, lidar_hardware_version, sdk_version, work_mode. Existing keys unchanged.
points_tempNNNN.binA 16-byte header and 48-byte records. Header-less temp files from older builds are still recovered.
imuNNNN.csv, packetsNNNN.binUnchanged.

LAZ: new extra bytes

The attributes are stored after the 28 standard bytes, in this order, and are described by the standard Extra Bytes VLR. Scale is 1 and offset is 0 for every attribute, so the stored numbers are in the units shown.

NameTypeByteUnitMeaning
rangefloat320mrange_scale * (ranges[j] + range_bias), the exact float the parser used for xyz
raw_rangeuint164mmranges[j] as sent by the L2
sample_indexuint166–j, the point's index in its packet (0..299). Filtered points leave gaps.
packet_sequint328–The packet's info.seq (wraps at 1024 on the L2)
alphafloat3212radThe alpha angle used for the point, bias included, accumulated as in the parser
thetafloat3216radThe theta angle used for the point, bias included, accumulated as in the parser. Not wrapped to [0, 2π).

Using them

  • Beam direction: computed from alpha, theta and the packet's beta_angle, xi_angle, a_axis_dist and b_axis_dist (from packetstateNNNN.tsv), using the sensor-model formula in docs/l2-recording-format.md. |xyz| differs from range by at most hypot(a_axis_dist, b_axis_dist).
  • Finding a point's packet row: points are written packet by packet. A new packet starts where packet_seq changes or sample_index does not increase. With that row, gps_time = stamp_ns/1e9 + sample_index · time_increment holds exactly.

New file: packetstateNNNN.tsv

Tab-separated with one header line. It has one row per point packet received while recording, in arrival order, including packets that yielded no point. Floats have 9 significant digits, which gives back the float32 exactly. A partial last row from a crash is trimmed on recovery.

Crash recovery

points_tempNNNN.bin now starts with the magic dLptsv2\n, the record size as uint32 (48) and 4 reserved bytes. A temp file without the magic comes from an older build: bare 32-byte records. It is still recovered, into a format 1 LAZ without extra bytes. Recovery also trims packetstateNNNN.tsv and moves it to recovered_<time>/ with the rest of the recording.

Repeating the check

Run tools/compare_recording_formats.sh [OLD_REV] [PACKETS_BIN] [SECONDS] [OUT_DIR] (defaults: d68191b, ~/PointCloudDump/packets0001.bin, the whole log, a temp directory). It builds tools/replay_capture.cpp against the old commit and against the working tree, replays the same packets through both, and runs tools/verify_recording_format.py. Set PYTHON to an interpreter that has laspy[lazrs] and numpy. bin/replay_capture packetsNNNN.bin out_dir [seconds] writes a single replayed recording.

Known differences and limits

  • Header differences that dMapper doesn't read: record length (48), generating_software, the Extra Bytes VLR, and the offset to the point data.
  • LAZ size grows about 2.4× (46 MB to 109 MB for 190 s), because the float extra bytes compress poorly.
  • laspy returns integer attributes as floats. LASzip always sets the scale/offset option bits, so laspy returns raw_range, sample_index and packet_seq as floats with the same values.
  • The firmware and hardware version query has not been tested on a real L2.
  • The live capture loop was not exercised. Chunk assembly moved into ChunkAssembler, which the replay exercises. The live ProcessSensorData loop was only compiled.
